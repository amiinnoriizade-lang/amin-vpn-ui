# AMIN Native Node API v1

Status: experimental implementation branch. This document describes the endpoints and Core integration that currently exist; it is not a production-readiness statement.
Compatibility: existing Sanaei nodes keep their current adapter. A node record explicitly marked as an AMIN Agent node uses the native API instead of Sanaei routes.

## Current Core integration

- The existing super-admin-only Nodes page can register a native Agent endpoint, probe it, and show synchronized inbound/client snapshots.
- The Core adapter calls Agent health, capabilities, system and inbound-list endpoints.
- VLESS, VMess and Trojan clients can be created on a selected native inbound and deleted from every inbound on that node where the username exists.
- Client identifiers are generated by Core (UUID for VLESS/VMess, random UUID-shaped password for Trojan); the credential is returned only in the authenticated create response.
- Agent 0.2.1 does not implement traffic quotas, expiry, client updates, share URI/QR generation or traffic counters. The native UI creates unlimited/no-expiry clients only and clearly reports these limitations.
- Node API tokens are not serialized to browser JSON (`ApiToken` has `json:"-"`), but the current node database column stores the token in plaintext. At-rest encryption, enrollment, token rotation/revocation and audit logging are not implemented yet.

## Secure transport

The Agent binds to `127.0.0.1:8787` by default and speaks HTTP. Do not expose that listener directly to the public internet. For a panel on another host, provide a private management path such as an SSH local forward from the Core host to the Agent's loopback listener, or terminate TLS in a properly configured reverse proxy. The Core adapter permits plain HTTP for native Agent nodes only when the operator explicitly enables private-address access and the resolved endpoint is private/loopback/link-local. Public endpoints must use HTTPS with normal certificate validation or a pinned certificate.

For an SSH local forward, the Node record must point to the *Core host's local forwarded address and port*, not to the Agent's remote loopback address. The node's public proxy address is a separate concern and is not inferred from the management tunnel.

## Agent API v1 currently implemented

All responses use the envelope `{"success":boolean,"msg":string,"obj":any}`.
All routes except `GET /health` require `Authorization: Bearer <node-token>`.

- `GET /health` — service name, Agent version and uptime.
- `GET /api/v1/capabilities` — Agent version, Xray-management availability, supported features and protocols.
- `GET /api/v1/system` — Go version, goroutine count, heap allocation, uptime, OS and architecture.
- `GET /api/v1/inbounds` — current Xray inbound objects from the configured Xray JSON file.
- `POST /api/v1/inbounds` — create an inbound.
- `DELETE /api/v1/inbounds/{tag}` — delete an inbound by tag.
- `POST /api/v1/inbounds/{tag}/clients` — create a client.
- `DELETE /api/v1/inbounds/{tag}/clients?email={email}` — delete a client by email from one inbound.

Client creation accepts only `email`, `id`, `level`, `flow`, `alterId`, `security` and `password`. VLESS/VMess require a UUID in `id`; Trojan/Shadowsocks require `password`. Core currently exposes VLESS, VMess and Trojan creation.

## Xray configuration safety

The Agent does not accept arbitrary shell commands or arbitrary filesystem paths from Core. It validates client fields against an allowlist, stages a new Xray config, runs the configured Xray binary in config-test mode, backs up the previous config, atomically replaces it and restarts the configured systemd service. If restart fails, it attempts to restore the previous config. Writes are serialized by an in-process mutex. Existing config ownership and permission bits are preserved.

## Not yet implemented

- Secure enrollment and token rotation/revocation; encrypted token storage at rest.
- Agent-side CPU/memory/network traffic metrics and per-client traffic counters.
- Client update/enable/disable and quota/expiry enforcement.
- Connection URI/QR generation for native Agent clients.
- Full audit trail, deployment hardening and install package.
- End-to-end integration over a provisioned private tunnel against a separate Core host.

Keep PR #11 in Draft while these items and a complete end-to-end test remain outstanding. Do not deploy this experimental integration to production.
